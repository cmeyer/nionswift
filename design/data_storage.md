# Nion Swift Data Storage

A project stores each data item's data, with the data item's properties, in a data file of its own, and stores its other items in its index file. This document describes how a project's file storage chooses, writes, reads, closes, removes and loads data files, and which threads touch a data item's data. The code is in `FileStorageSystem.py`, `NDataHandler.py`, `HDF5Handler.py`, `DataHandle.py` and the data handling of `DataItem.py`. Tests also use `MemoryProjectStorageSystem`, which holds the same content in dictionaries.

## Terms

A **data file** holds one data item's data and its properties. It is an ndata file (`.ndata`) or an HDF5 file (`.h5`). A storage handler, `NDataHandler` or `HDF5Handler`, reads and writes one data file, and the project's storage, `FileProjectStorageSystem`, keeps one for each data item.

A project's **data folder** holds its data files. A data file's path in it is `<year>/<month>/<day>/<session>/<stem>.<extension>`, made from the data item's creation date, its session and a stem, `data_` followed by an encoding of its uuid. The date and session folders are historical, from when it was not yet known whether users would browse the data folder directly. Users are not expected to, but the folders still keep any one folder from holding every data file of a project. The storage finds data files by reading the whole data folder. A file whose stem is that of its data item is **named for** the data item.

A **pending file** holds an HDF5 data item's new data and properties beside its data file, under the hidden name `.<stem>.<n>.h5`, until it replaces the data file. The code calls the data file which a pending file replaces the canonical file. A **ready file**, `.<stem>.ready.h5`, is a synced pending file whose replace was still refused when its project closed.

A data item's **properties** are its persistent properties, among them its data's shape, dtype and descriptor, its calibrations, its metadata, its session and its `modified` time. Keeping the properties in the data file rather than the index file is a historical choice, which makes migrating a project slow, since a migration touches every data file, and limits a data file to formats which can hold and quickly update the properties; https://github.com/nion-software/nionswift/issues/1264 proposes moving them to the index file.

## How it works

### File type

A data item whose data takes more than 16 MiB is stored in an HDF5 file, and any other in an ndata file. HDF5 data can be read and written in part without loading all of it into memory. ndata data is read into memory as a numpy array, which supports every numpy operation, and an ndata file can be read without a third-party library. A test can set another limit, to store small data in HDF5, through the profile's `ProjectStorageSettings`, which the profile passes to index projects only.

When written or reserved data crosses the limit, the storage replaces the data item's file with one of the other type, at the path for the data item's current session. It deletes the old file, writes the properties into the new one, and then writes the data. An old HDF5 file whose data is held is deleted after the last holder lets go.

### What each file holds

An ndata file is an uncompressed zip of `data.npy` and `metadata.json`, which holds the properties, with the data first. Writing or reserving data rewrites the whole file in place and keeps its properties. Writing properties rewrites `metadata.json` and the zip directory after the data when the data comes first, and otherwise the whole file. Each ndata write sets the file's modification time to the data item's creation time.

An HDF5 file holds one dataset, `data`, with the properties as JSON in its `properties` attribute. Data of the dataset's shape and dtype is written into the dataset. Data of another shape or dtype, and any reserve into a file which has a dataset, goes into a new pending file with a copy of the `properties` attribute, which then replaces the file (see Replacing HDF5 data). Writing properties to a file which has no dataset creates an empty one of shape (0,), which reads as no data. Each handler opens its own h5py file on first use and keeps it open until a reshape, a reserve, a storage type change or a removal gives it up, or until it has been idle for a while (see Closing HDF5 files). The next use opens the file at its path again.

### Reading

A data item loads its data from its file when the first reference to the data is taken, and drops it when the last reference goes, once the data is written to the file. It also drops data loaded from HDF5 while it is referenced, when its pending file waits only for that data (see Replacing HDF5 data), and loads it again when the data is next taken. ndata data is read into memory. HDF5 data is a data handle, `DataHandle`, over the h5py dataset, which the handle doesn't expose. The handle has the interface of an h5py dataset: indexing it reads that part of the file into a numpy array, converting it to numpy reads all of it, and assigning to an index writes into the file, as a partial update does. Numpy arithmetic and most array methods need it converted to numpy first. The handler hands out the same handle for its current dataset for as long as anyone holds it, and keeps only a weak reference to it, so that it can tell whether anyone holds it. When a reshape, a reserve, a storage type change or a removal gives up the file of a held handle, the file stays open for the holders, who keep reading the earlier data. The handle then refuses writes, raising `ValueError`.

When a data item's data is set from data which is not a numpy array, such as another item's data handle or a view of one, the item drops that data once its file holds it, since it would keep the other item's file open. The item loads its own data from its file in its place when its data is next taken.

### Writing

When a data item's data is set or partially updated, when the data item is inserted into a project, and when its write delay ends, it writes its data and then the properties which describe the data. HDF5 data of a new shape or dtype goes into a pending file, the new properties then go into the pending file too, and the data item's file keeps its previous data and the properties which describe it until the pending file replaces it. A reserve first replaces the file's data with data of the new shape and dtype, which reads as zeros, keeping the file's properties, and then writes the properties which describe the new shape; for HDF5 data over existing data, it too goes through a pending file. Each change to a property rewrites all of the data item's properties. While a data item's writes are delayed, as in a transaction, it keeps its data in memory and writes its data and properties when the delay ends; a reserve still writes its data at once, and a partial update to HDF5 data still writes into the file through the data handle, while the properties which describe them, and so the replacement by a pending file, wait for the delay to end.

A partial update to ndata data changes the data in memory and rewrites the whole file. A partial update to HDF5 data writes the slice into the file through the data handle, and the storage then flushes the file. A data item whose data was set from data which is not a numpy array, such as another item's data handle, keeps that data while its writes are delayed; a partial update then first copies it into memory, so that the update changes only this data item. That costs memory for the whole data, as setting a numpy array in a transaction does.

Setting or partially updating data records the current session on the data item. The session chooses the folder of a file made later, by a storage type change or a restore; an existing file stays where it is. It is recorded before the data is written, so that a storage type change during the write puts the new file in the current session's folder.

### Replacing HDF5 data

When an HDF5 data item's data changes shape or dtype, or is reserved, its handler writes a pending file holding the new data, or zeros for a reserve, and a copy of the current properties. The handler then gives up its current file and continues with the pending file, to which all reads and writes go, properties included, while the data item's file keeps its previous data and properties. A newer pending file supersedes an older one, which is deleted once nothing in this process has it open.

A storage type change back to HDF5 can make a handler for the path of the data item's earlier HDF5 file while that file waits to be deleted, as it does when the file is in the current session's folder and its data is held. The handler keeps the file with its data and the properties which describe it, and writes its first data or reserve to a pending file whatever the shape, together with the properties it is given before then. The holders keep reading the earlier data, and the pending file replaces the file once the holders let go.

The pending file replaces the data item's file, by a rename over it, once it holds the properties which describe its data, a sync of it has finished which covers every write into it, nothing in this process has the data item's file open, and nobody holds the pending file's data handle. A `close_released_files` once the pending file has had no writes, through the handler or through its data handle, for the idle delay (see Closing HDF5 files) requests that sync from a sync thread and doesn't wait for it, and a later `close_released_files` completes the replacement if it can. A write through a data handle is timed from the `close_released_files` which finds it. A pending file written more often than the delay, as by a live acquisition, isn't synced until its writes stop, and a write after the sync was requested makes the replacement wait for another sync. The sync makes the data durable before the rename, so that a power loss after the rename leaves a readable file. The sync uses `F_FULLFSYNC` on macOS, since `fsync` there doesn't flush the drive's cache, and falls back to `fsync` on a file system without it. A sync which the file system refuses leaves the pending file in place until a later call.

A displayed data item holds its data, and with it the pending file's data handle, for as long as it is displayed. When the pending file waits only for its data handle, the document model asks the data item to drop the data it loaded; the data item drops it and has the storage complete the replacement while it holds its lock, so that a reader on another thread then loads the data from the replaced file. A reader which took the data before keeps the pending file open, and the replacement waits for a later call. A data item whose writes are delayed, as in a transaction, keeps its data, since the pending file doesn't yet hold the properties which describe the writes made meanwhile, so that a crash then loads the data item's file with its previous data and properties. Loading the data again makes a new data handle on the replaced file, which reads nothing until it is indexed.

Windows refuses the replace while another process has the data item's file open, such as a cloud sync client, a virus scanner or a program which opened the file. A replace is stuck once the file system has refused it for a minute since its first refusal, by the settings' clock. After each `close_released_files` in which replacements became stuck, the document model fires `data_file_replacements_stuck_event` with the data file and data item of each, and each replacement is reported once. The document window shows the stuck replacements in a dialog which doesn't block, with one line for each file, and holds those reported while it is open for the next dialog, so that at most one is open. The next dialog leaves out the files whose replace has since completed, and doesn't open if none is left. A test can set the delay through `ProjectStorageSettings`.

Closing the project waits for the syncs of the pending files which the handlers still have. A pending file which doesn't hold the properties which describe its data, or whose sync is refused, is deleted when its handler closes, and the data item's file keeps its previous data and properties. Closing tries the replaces which are refused again, with short waits, for two seconds in all. A synced pending file whose replace is still refused then records the `modified` property of the data item's file, in its dataset's `ready_canonical_modified` attribute, and is synced again and renamed to its ready file. A refused rename is tried again, with short waits, for one second in all across the pending files, since a virus scanner may open a file as its last handle closes, and the two seconds are spent by then. The value comes from when the handler started pending: from the data item's file, which isn't written while it has a pending file, or from the record of the ready file on which the handler started, and a pending file which supersedes another or which a restore brings back keeps it. Another program which refuses reads of the data item's file at the close doesn't stop the record. The sync comes before the rename, so that a power loss can't leave a ready file with a damaged record. The next load completes the replace (see Loading). Earlier versions skip the ready file, and load the data item's file with its previous data and the properties which describe it. A pending file stays, and the next load deletes it, if that value couldn't be read when the handler started pending or the rename is still refused, either of which is logged on the `loader` log. A test can set the time of these tries through `ProjectStorageSettings`.

A handler which started on a ready file (see Loading) doesn't delete it when a newer pending file supersedes it or when its sync is refused at close, since an earlier session saved its data. The ready file keeps the record made when it became ready, and the next load decides whether it replaces the data item's file.

A pending file's syncs are the only syncs: the renames and the folder aren't synced, since a rename which a power loss undoes leaves the data item's file with its previous data, and a write doesn't sync the file. Nothing in this process renames, moves or deletes an HDF5 data file it has open, since Windows refuses that, so the same steps run on every platform. A rename or delete which is refused is tried again at the next call, and one still refused when the project closes is left for the next load, except the replace by a synced pending file, above.

A crash while a file is pending leaves the data item's file with its previous data and the properties which describe it, which every version loads, since every version skips files whose names begin with ".". The next load of this version deletes the pending file (see Loading).

### Closing HDF5 files

A handler gives up its HDF5 file when it closes, and for a reshape, a reserve, a storage type change or a removal. It closes a file whose data handle nobody holds. It retires a file whose data handle is held: the file stays open for the holders, and the handler continues with a new file.

The document model calls `close_released_files` on the main thread about once a second, from a task on its event loop. It closes the retired files whose last holder has gone, deletes the files waiting to be deleted, moves removed files into the trash (see Removing and restoring), requests the syncs of pending files which have had no writes for the idle delay, completes the replacements by pending files, and then closes the idle files. Before it, the document model has each data item whose pending file waits only for its data handle drop its loaded data (see Replacing HDF5 data). Closing the project closes every retired file, whether or not its holders have gone, and then does the same deletes, moves and replacements.

A handler's current file becomes idle when the last holder of its data handle lets go, and after each use while nobody holds the handle. `close_released_files` closes a file which has been idle for five seconds, and the next use opens it again. This keeps a session from keeping many files open; https://github.com/nion-software/nionswift/issues/1006 reports "Too many open files" on Linux. The same delay times the syncs of pending files (see Replacing HDF5 data). A test can set another delay, and the clock which times it, through `ProjectStorageSettings`.

### Removing and restoring

Removing a data item moves its file into the `trash` folder of the data folder, or deletes the file if the trash already holds one of that name. An HDF5 file whose data handle is held stays at its path instead, open for its holders. The storage marks it removed by setting the `version` in its properties to -1, and `close_released_files` moves it into the trash once nothing in this process has it open. Every version skips a data file of a version it doesn't write, so none loads a file marked removed. An HDF5 file whose move into the trash is refused is marked removed in the same way and moved at a later call. A file whose move is still refused when the project closes stays at its path, marked removed, and the next load deletes it. When a data item is removed while a file is pending, its data file, which holds the previous data, is marked removed, and its pending file moves into the trash under the data file's name once nothing in this process has it open and its sync has finished. A removed pending file whose sync hasn't finished when the project closes stays at its path, and the next load deletes it. The data file is deleted once the pending file has moved, so that a restore before then finds both files. Another program may refuse the mark of the data file, as it may refuse the replace which the removal follows. The removal then goes on, and the mark is tried again at each `close_released_files` until the data file is marked or deleted. If the mark is still refused when the project closes, which is logged on the `loader` log, the next load loads the data item from the data file, with its previous data and no display item, since the project no longer holds one. Files which the storage replaces itself, such as a superseded pending file or the old file of a storage type change, are deleted, unless a storage type change back to HDF5 keeps the old file (see Replacing HDF5 data).

Restoring the data item, required for undo, takes back a removed file which hasn't yet moved into the trash, and removes its mark, except from a data file which refused it. The data item then uses the file where it is, while the file's earlier holders keep reading it; that path may differ from the path for its current session. A removed pending file becomes the data item's pending file again, and the data item's file, if it is still there, is kept and its mark removed. Otherwise restoring finds the file in the trash which holds it, looking first at the files named for it, removes any mark, and moves that file back to the path for its creation date and session, unless a file is already at that path. When the file at that path is the data item's earlier file, waiting to be deleted while it is open, the file from the trash becomes a pending file which replaces it. An undo first checks that each file in the trash named for the data item can be moved, by renaming it to a hidden name and back, that each file which it has to write at its path can be renamed, by renaming it to its own name unless this process has it open, and that each file which it has to write accepts writes, including the data item's HDF5 file in the trash, so that a refusal leaves the items of that removal as they were. The renames come first, since Windows refuses them while another program has the file open, and h5py raises a plain `OSError` there for a file which another program has locked, as it does for a damaged file. Only a refusal of access, or an HDF5 file lock which another program holds, refuses the undo. Any other error, such as from a damaged HDF5 file, fails the undo, and the undo leaves the undo stack. A damaged ndata file in the trash doesn't fail the undo; as in earlier versions, the display item comes back without its data item. When one refuses, the data item stays removed, the undo stays on the undo stack for a later undo, and the document window reports it in a dialog which doesn't block. The items of the command's other removals which were already restored stay restored. A data item which stays removed when the project closes is treated as any other removal: its files go at the next load, or stay marked removed while they refuse the delete. The trash keeps a removed data item's data, which may be too large to keep in memory, so that undo can restore it. The trash is emptied each time the project is opened, as it historically has been; https://github.com/nion-software/nionswift/issues/123 proposes a trash which the user views and empties.

### Finding the data folder

The data folder is the folder beside the index file with the index file's name, without its extension, and " Data" appended, if it exists, and otherwise the first existing folder among those listed in the index file's `project_data_folders`. If none of them exists, it is the folder beside the index file with " Data" appended, which is made when the first data file is written. Each write of the index file records the data folder in `project_data_folders`, relative to the index file's folder when it is beside the index file.

### Loading

At load the storage first deletes the pending files in the data folder which a session left behind. The data item's file beside each holds its data and the properties which describe it as they were before the pending file was made. A delete which is refused is logged on the `loader` log and tried again at the next load.

Each ready file then replaces its data item's file. A ready file whose data item's file is gone, as when an earlier version removed the data item, is deleted. So is a ready file whose properties or record can't be read, a ready file whose data item's file isn't of the version this nionswift writes, as when it is marked removed, and a ready file whose record differs from the `modified` property of the data item's file, each of which is logged on the `loader` log with the data item's file. A different value means that the file changed after the close: an earlier version, which skips the ready file, changed the data item, or a newer pending file replaced the file. The values have to be equal since the clocks of different machines can't be compared; a data item's file with no `modified` property matches a record of none. A data item's file whose properties can't be read is replaced, since the load couldn't use it. When the replace is refused, which is logged on the `loader` log, the ready file becomes the data item's pending file, so that the data item loads the data saved last, and the replace is tried again at each `close_released_files`.

It then reads the properties of every data file in the data folder, except files in the trash and files whose names begin with ".". Every `.h5` file is read as an HDF5 data file, and an `.ndata` file is read as an ndata data file if it is a zip which holds `data.npy`, `metadata.json` or both, and nothing else. A file whose properties or uuid cannot be read is reported as a reader error, closed and left in place. A file marked removed is deleted, and one which cannot be deleted is logged on the `loader` log and skipped again at the next load. Data items are loaded from the files of the version this nionswift writes, in order of their creation time.

When a data item matches more than one file of the data item version this nionswift writes, it takes its properties and its data from the one with the newest `modified` in its properties, then the one named for the data item, then the first by path. The others are deleted. A file which cannot be deleted is logged on the `loader` log. A file of another data item version is never chosen and never deleted, since it may be the only copy another version of nionswift reads. A data item whose files are all of another version is not loaded.

### Threads

The main thread sets, reserves and partially updates a data item's data, writes its file, and removes, restores and loads data items. Acquisition and other threads queue new data and partial updates on the document model, and the main thread applies them. Computation and display threads read a data item's data through `xdata`, which may load the data from the file on that thread. The main thread closes released and idle HDF5 files in `close_released_files`. Each project's storage has one sync thread, which its first request starts. The thread syncs the pending files in the order requested, one request per file, through a handle of its own, and takes no data item lock and no storage handler lock. A request still waiting is dropped when its pending file is deleted or replaces the data item's file. The thread's condition guards the requests, and the thread holds it only to take one. The thread prints the traceback of a sync which fails with an unexpected error, once until the file syncs, and finishes the sync with the error, as a refused one; a sync requested after the project closes finishes at once with an error. The main thread never waits for a sync, except when the project closes (see Replacing HDF5 data), which then stops the sync thread. Closing the project also waits between the tries of refused replaces and of refused renames to ready files. A data handle's finalizer may run on any thread, inside unrelated code, so it takes no lock and only adds the handle's file to a queue, and `close_released_files` takes the files from it. The main thread never waits for a storage handler's lock to close an idle file or complete a replacement: it skips a handler which is in use on another thread until the next call. A write through a data handle and the handler marking the handle replaced both take the handle's lock, so that each write either finishes before the mark or is refused.

A data item's lock, `__data_ref_count_mutex` in `DataItem`, guards its loaded data, its data metadata and its data reference count. Dropping loaded data for a pending file holds the lock from the drop through the storage's replacement. Loading data reads the file while holding the lock. A set assigns the data and its data metadata together under the lock and writes the file after releasing it. A reserve holds the lock from dropping the loaded data, through the storage's reserve and any storage type change, to loading the reserved data, and writes the properties after releasing it. `xdata` reads the data and its data metadata together under the lock, so that a display or computation thread gets both from the same set or reserve. A partial update writes into the data the item already holds, of the same shape and dtype, without the lock, since the lock guards which data and data metadata a reader takes and not the values in the data. Locks are taken in one order: a data item's lock, then its storage handler's lock, then any one of the locks of the HDF5 file entry, the data handle, the deferred files and their sync condition. Loading, reserving and dropping loaded data for a pending file call into the storage while holding the data item's lock, so the storage code doesn't take that lock, since a thread taking it inside a storage lock could deadlock with one taking them in order.

### Data files log

The logger `nion.swift.data_files` records each data file created, written, reserved, moved, replaced and deleted, each storage type change, each ndata read and properties rewrite, and each HDF5 write through the data handle. For HDF5 files it also records each file opened, closed, with the reason, retired and marked removed, each replacement by a pending file started and superseded, each data item which drops its loaded data for one, each sync which is refused, each repeat of a sync's unexpected error, each delete, move, rename or mark which is refused, each replacement which becomes stuck, and each ready file whose replace is refused at load. After each `close_released_files` which changes anything, it records how many HDF5 files this process has open, and how many of the project's are idle, retired and pending. All its records are at DEBUG. Turn it on with `logging.getLogger("nion.swift.data_files").setLevel(logging.DEBUG)`, for example from the console or a debugger; its records then go to stderr through the handler the application adds to the root logger.
